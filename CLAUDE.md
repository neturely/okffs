# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

**okffs** is a TypeScript/Node.js MCP server that connects Claude Code to GitHub, enabling a full **issue → branch → merge → close** workflow. The goal: discuss tasks in Claude.ai, then push them to GitHub as issues and branches in one shot via Claude Code.

## Stack

- TypeScript / Node.js MCP server
- GitHub Personal Access Token (PAT) authentication (upgrade to a GitHub App later)
- Published to npm (package name: `@neturely/okffs`) and the MCP Registry (`registry.modelcontextprotocol.io`)

## Conventions

- **Destructive tools require `confirmed: true`** — call once for a warning, re-call to proceed.
- **GitHub is the source of truth** for issue state, never local.
- **Keep the tool surface minimal** — do one thing well per tool.
- **Destructive actions post a comment to the issue before acting.**
- **Always reach for an okffs tool before raw `git`/`gh`/GraphQL** when one covers the action — a correctness rule, not a style preference. okffs authenticates with the configured `GITHUB_TOKEN` (scoped for this repo, incl. Projects/org Issue Fields), whereas raw `gh`/`git` uses whatever ambient CLI token is signed in — often the wrong identity or missing scopes; and okffs applies the conventions (branch naming, the **Branch:** link, `Closes #N`, board placement, changelog fragments, the `OKFFS_PROTECTED_BRANCH` invariant) that hand-rolled commands silently skip. When an okffs tool covers the action — issues, PRs (`create_pull_request` for an issue's PR; **`promote_branch` for a base→protected promotion like `develop → main`**, never raw `gh pr create`; **`fix_into_base` for an issue-less fix PR into the base branch**, never raw `gh pr create`/`gh pr merge`), comments, review threads (`resolve_review_thread` / the `address_pr_review` prompt), releases (`prepare_release`), project status — use it and honour its env toggles (`OKFFS_RESOLVE_THREADS`, `OKFFS_BASE_BRANCH`, `OKFFS_PROTECTED_BRANCH`, `OKFFS_PROMOTION_*`, …) rather than re-deriving the behaviour. Fall back to raw `git`/`gh` only when no okffs tool fits. Never merge/tag/publish into `OKFFS_PROTECTED_BRANCH` autonomously (okffs may *open* a PR into it, but not merge) — hand back to the user.

### Branch naming

`{issue-number}-{kebab-title-slug}` — title truncated to ~5 words, no forward slashes.

```
42-add-hero-section-to-homepage
```

When `OKFFS_IDENTIFIER` is set, a project-scoped prefix is inserted: `{issue-number}-{identifier}-{kebab-title-slug}`.

```
42-okffs-add-hero-section-to-homepage
```

### Pull requests

- Title: `Close #42 - Add hero section to homepage`
- Body **always** includes `Closes #42` — this triggers GitHub's native auto-close **only when the PR merges into the repository's default branch** (usually `main`). If `OKFFS_BASE_BRANCH` points at a non-default branch (e.g. `develop`), GitHub will **not** auto-close the issue on merge — close it manually with `close_issue`. `create_pull_request` warns when the PR targets a non-default base.

## Build phases

### Phase 1 — Core MCP server ✓ Complete

- TypeScript MCP server scaffolded.
- PAT auth via `.env` (`GITHUB_TOKEN`, `GITHUB_OWNER`, `GITHUB_REPO`).
- `.env` is loaded automatically at startup — the working directory's `.env` over the git root's (#308) — no `--env-file` flag needed in `.mcp.json`.
- Tools: `create_issue`, `list_issues`, `close_issue`, `delete_issue`, `delete_branch`, `get_issue`, `comment_issue`, `link_issues`, `create_issues_from_list`, `plan`, `create_pull_request`, `commit_and_update`, `list_pr_review_comments`, `reply_to_review_comment`, `resolve_review_thread`, `prepare_release`, `update_project_status`, `set_issue_fields`, `update_issue`, `promote_branch`, `merge_pull_request`, `fix_into_base`, `configure`.
- Prompts (MCP `prompts` capability, surfaced as slash commands): `address_pr_review` — read a PR's review comments, fix the valid ones, reply per thread, post a summary, and optionally resolve threads; `update_guidance` — review an issue's changes and intelligently maintain the bounded `## Project Guidance (okffs usage)` section of CLAUDE.md to reflect new/changed functionality (substantive, marker-delimited; never touches the user's other content); `setup` — configure okffs conversationally in Claude Code (the in-chat counterpart to the `okffs setup` CLI), interviewing the user from the env-var manifest and persisting via the `configure` tool.
- **`okffs setup` CLI** — beyond the MCP server, okffs ships a `bin` CLI (`npx @neturely/okffs setup`, or `node dist/cli/index.js setup` locally). `src/index.ts` is a thin dispatcher: CLI subcommands route to `src/cli/`, and with no args it dynamically imports the stdio server (`src/server.ts`) — so the CLI path never triggers `github.ts`'s import-time token/repo resolution (which throws when unconfigured, exactly the state `setup` runs in).
- `create_issue` auto-creates a branch, embeds the branch name in the issue body (**except for Epics**, #323: a requested/resolved type of `Epic` gets no branch, **Branch:** line, init commit or draft PR — a draft PR's `Closes #N` would close the epic on merge while its children are open; board/labels/type/relationships still apply, and `commit_and_update` / `create_pull_request` on an epic return an actionable pointer to the children — pure decision in `src/epic.ts`, applied by `plan` / `create_issues_from_list` too), applies default assignees/labels from `.env`, infers labels from title/description and merges with `OKFFS_DEFAULT_LABELS`. Supports optional `assignees`, `labels`, `milestone`. If a relationship is mentioned (blocked by, blocking, parent), automatically calls `link_issues` after creation. If `OKFFS_AUTO_PR=true`, pushes an empty init commit to the branch (capturing and restoring the current branch) and opens a draft PR immediately.
- `create_issues_from_list` accepts a list of tasks and creates all issues + branches in one shot. Two-step confirmation. Per-task `labels`, `assignees`, and `milestone` supported.
- `plan` takes a free-text `description` plus the issue breakdown Claude generates from it (titles, descriptions, labels, inter-task relationships referenced by 1-based index) and creates all issues + branches in one shot. Two-step confirmation (preview, then `confirmed: true`). Resolves task-index relationships to real issue numbers and writes them to each issue's `## Relationships` section. If `OKFFS_AUTO_PR=true`, pushes an empty init commit per branch and opens a draft PR for each. Extends the `create_issues_from_list` pattern — Claude is the AI layer that produces the breakdown.
- `list_issues` returns each open issue with its issue URL, branch name + URL, any matched open/draft PR (by head branch), its board column (`project:`), its `priority:`, its native Issue Type (`type:`, when the org defines them — read straight off the issue object, no extra fetch), and its relationships (parent, children, blocked-by, blocking) rendered as a tree. Issues are **ordered by Priority** (Urgent → High → Medium → Low → unset) so the most important work surfaces first — the agent factors Priority in when deciding what to do next. Priority is read from the project-native Priority field, or the org-level Issue Field when `OKFFS_CLASSIC_PAT=true`. Children are derived by inverting `Parent:` links across issues. When an open promotion PR (`OKFFS_BASE_BRANCH` → `OKFFS_PROTECTED_BRANCH`) has **unresolved review threads**, a "Release gate" header surfaces them at the top of the listing (even with zero open issues); a clean gate adds nothing (#302). Replaces the need for a separate PR-listing tool.
- `get_issue` fetches full issue details — title, body, status, branch, assignees, labels.
- `comment_issue` posts a comment to an issue. Use after committing to log what was done. Pass an optional `marker` (letters/digits/`.`/`-`/`_`) to **upsert** instead (#267): the comment carrying that hidden HTML-comment marker is edited in place, or created if absent — one running status comment per issue instead of an append-only thread.
- `link_issues` links two issues with a relationship — `blocked_by`, `blocking`, or `parent`. Stored in the issue body under a `## Relationships` section.
- `close_issue` closes the issue and returns a tip suggesting the user runs `/clear` in Claude Code to reset context before the next issue. (Under `OKFFS_AUTO_PR=true` the draft PR already exists from `create_issue`, so no PR is created here.)
- `commit_and_update` stages **tracked, modified files only** by default (`git add -u`); untracked/new files require `include_untracked: true` — the silent add-all sweep of scratch/backup files is how live secrets got committed (#265). A **secrets deny-list** (`.env*`, `*.env`, `*.pem`, `*.key`, `id_rsa*`, `*credentials*`, `*.p12`, `*.pfx` — matched on basename, case-insensitive; template files ending `.example`/`.sample`/`.template` are exempt) refuses the whole call listing the offenders unless `allow_secret_paths: true` — checked both before staging and against the staged list, so pre-staged index entries can't slip through. **`message` is the canonical commit-message param** (#290; the one-release `hint` alias was removed in #297), used **verbatim** (word-boundary subject/body split); an absent message auto-generates one that never truncates the file list. Unknown params (e.g. `commit_message`, or the removed `hint`) are rejected with an actionable error naming the canonical param, never silently stripped. The tool result and issue comment carry the full staged file list with per-file +/- counts, plus any skipped untracked files. Commits, pushes to the issue branch, and posts a rich progress comment to the linked issue. Idempotent on retry (#269): a clean tree whose HEAD already matches the remote branch tip (the earlier invocation landed but the client timed out) is treated as success — the existing commit hash is reused and the comment still posts, marked as an idempotent retry; a clean tree not yet pushed gets a friendly "nothing to commit" message instead of a raw git error. No code path escapes as a raw MCP -32603 (#284): an issue-lookup failure returns a contextual error (nothing committed), and a comment-post failure after the durable commit+push returns success-with-warning carrying the commit hash + branch — retry just the comment with `comment_issue`, never redo the commit. All GitHub REST/GraphQL fetches carry a 30s timeout; only GETs are retried (once) — writes never are, to avoid double-applying.
- `list_pr_review_comments` fetches a PR's review feedback via GraphQL — inline threads (comment ids, file/line, author, body, resolved state, thread ids) and review summaries. The agent reads these, fixes, then replies/resolves.
- `reply_to_review_comment` replies to an inline review comment thread by id (REST `in_reply_to`).
- `resolve_review_thread` resolves a review thread (GraphQL). Gated by `OKFFS_RESOLVE_THREADS`: declines unless that env var is `true`, leaving threads for the user to resolve manually.
- `address_pr_review` (MCP prompt / slash command) orchestrates the loop: `list_pr_review_comments` → triage + fix → `commit_and_update` → `reply_to_review_comment` per thread → `comment_issue` summary → `resolve_review_thread` (respects `OKFFS_RESOLVE_THREADS`). The host LLM provides triage/fixes; okffs provides the plumbing. When the reviewed PR's head is a protected integration branch you can't push to directly — a promotion/gate PR like `develop → main` — fixes can't commit onto the head; instead they route through **`fix_into_base`** (issue-less, #226): a scratch branch off the integration branch, a raw-git commit (not `commit_and_update`, which requires an issue number), then `fix_into_base` opens+merges a PR into the head/integration branch. Threads are only resolved **after** that PR merges (resolving while the fix sits in an unmerged PR is misleading). Do **not** spin up a follow-up issue + `create_issue` + `create_pull_request` for this — that pre-#226 route leaves a merge-order hazard `fix_into_base`'s gated merge avoids. Complete the loop — don't leave a dangling PR. Never merge into `OKFFS_PROTECTED_BRANCH` autonomously (#192, #255).
- `prepare_release` bumps the version — `package.json` (+ `package-lock.json` when present), else a plain `VERSION` file (`X.Y.Z`), created on the first release with a warning when neither exists (#307) — rolls the CHANGELOG (`[Unreleased]` → `## [X.Y.Z] - <date>`, fresh empty `[Unreleased]`, updated compare links), commits on a `release/X.Y.Z` branch (`release/{app}-X.Y.Z` under multisite) off `OKFFS_BASE_BRANCH`, and opens a PR. Takes an optional `app` (#332: release that registry app from anywhere — its `<app>/CHANGELOG.md`, fragments, version source and tag prefix; defaults to the session's `OKFFS_APP`; a root session of a multisite repo with neither is refused with the list of apps), an explicit `version` or a `bump` level; if neither, infers the level from `[Unreleased]` (`### Added` → minor, else patch) and surfaces it. Two-step confirmation. It does **not** tag or publish — tag `vX.Y.Z` after merge to trigger the CI npm publish.
- `promote_branch` opens the **issue-less** release/promotion PR from one long-lived branch into another — e.g. `develop → main`. Use it instead of raw `gh pr create` for a base→protected promotion. Head defaults to `OKFFS_BASE_BRANCH`, base to `OKFFS_PROTECTED_BRANCH` (else the repo default); both overridable. No `Closes #N`, and **no confirmation** — opening a PR is safe and reversible (the merge/tag are the user-gated steps okffs never drives). Adds the **PR itself** to the Projects v2 board as a card (Projects v2 accepts PRs as first-class items), optionally into `OKFFS_PROMOTION_STATUS`, and — when `OKFFS_PROMOTION_AUTO_REVIEW=true` — requests `OKFFS_PROMOTION_REVIEWERS` (e.g. Copilot) **on PR creation only** (never on re-runs, to avoid repeat/billable reviews) — all best-effort, surfaced in the response, never blocking. Reuses an already-open PR for the head→base rather than erroring — and on such a **re-run reports the gate PR's unresolved review threads** (count + reviewers + the address_pr_review loop to run, fixes via `fix_into_base`) without re-requesting the billable review, so re-running `promote_branch` is the way to check the release gate for landed Copilot feedback (#302; pure summarization in `src/review_gate.ts`). okffs opens and hands back; it never merges (#182, #194). **Release summary** (#312): the PR body gets a `## Releases in this promotion` section and the response a `📦 Releases carried:` note listing each app whose version (package.json/VERSION) differs between the head tip and the base tip — `finance 1.2.0 → 1.3.0 (finance-1.3.0)`, `vX.Y.Z` single-site, first releases marked — i.e. exactly the tags the merge will yield; nothing is added when the promotion carries no release (pure `src/release_summary.ts`; version probing shared with tagging in `src/app_versions.ts`). **`OKFFS_TAG_RELEASE=true`** (#310): a re-run **after the gate PR is merged** finds the latest merged head→base PR and tags the release(s) it carried on the PR's **merge commit** via the git-refs API — `vX.Y.Z` single-site, or `{app}-X.Y.Z` for each registry app whose version (package.json/VERSION, at `{app}/` or the session's own dir) differs between the merge commit and its first parent. Idempotent (a tag already at the merge commit is a quiet no-op); an unchanged version or missing version file is silent. Correctness stops, reported not prompted: the target tip moved past the merge commit, or the tag exists on another commit. Pure decision in `src/tagging.ts`; the tag is the deliverable — GitHub Release entries stay with CI (`publish.yml`). **`OKFFS_AUTO_MERGE_PROTECTED=true`** (#311): a re-run over an **existing** gate PR (never the creating call, so a requested review can land) merges it into `OKFFS_PROTECTED_BRANCH` with `OKFFS_PROTECTED_MERGE_METHOD` once every gate passes — the same gates as `merge_pull_request`, shared in `src/pr_gates.ts` (open, non-draft, conflict-free, not behind/blocked, all statuses + check runs green, **no pending requested reviewer**, every thread resolved) — and with `OKFFS_TAG_RELEASE=true` tags in the same call: the fully handled promotion (open → review lands → address → re-run merges + tags). Any unmet gate is reported and the PR stays open. This is the only way okffs merges the protected branch; it reverses the #192/#211/#255 invariant only under this explicit opt-in.
- `merge_pull_request` is the **one okffs tool that merges** — every other tool only opens PRs and hands back. It autonomously merges a **green, review-resolved PR into the base branch** (e.g. `develop`) using `OKFFS_BASE_MERGE_METHOD` (default `squash`). Takes **exactly one** of `issue_number` (the issue's PR — then comments on the issue and, when the base isn't the repo default so `Closes #N` won't auto-close, closes it to complete the loop) **or `pr_number`** (issue-less **merge-only** mode for a fix PR into the base branch — skips the issue lookup/comment/close and needs no **Branch:** line; #224). Passing neither/both returns an actionable `[okffs]` message. **Opt-in and heavily gated** (#211): does nothing unless `OKFFS_AUTO_MERGE_BASE=true`; refuses if `OKFFS_PROTECTED_BRANCH` is unset; only ever merges the base tier and **never** `OKFFS_PROTECTED_BRANCH`; and independently verifies (not trusting branch-protection rules) that the PR is open/non-draft/conflict-free, that **all** commit statuses **and** check runs are green (no failing/pending), that GitHub doesn't report it `blocked`/`behind`, and that **every** review thread is resolved. Any unmet gate → an actionable `[okffs]` refusal, no merge. The `develop → main` promotion stays a manual, user-driven merge/tag (`promote_branch` opens it; you merge) — unless you opt in with `OKFFS_AUTO_MERGE_PROTECTED` / `OKFFS_TAG_RELEASE`, in which case a `promote_branch` re-run drives it under the same gates (#311); `merge_pull_request` itself never touches the protected branch.
- `fix_into_base` is the issue-less **mirror of `promote_branch`** for the base tier (#226): it opens (and, when opted in, merges) an **issue-less fix PR into the base branch** — the last uncovered path (`create_pull_request` is issue-based; `promote_branch` is base→**protected** only; `merge_pull_request` merges into base but is otherwise issue-bound). Use it for a small fix that doesn't warrant its own issue (e.g. review-comment cleanups) instead of raw `gh pr create` + `gh pr merge`. `head` defaults to the current branch, `base` to `OKFFS_BASE_BRANCH` (else the repo default); it pushes the head, writes no `Closes #N` / needs no **Branch:** line, reuses an already-open head→base PR, and best-effort boards the PR (like `promote_branch`, into `OKFFS_PROMOTION_STATUS`). Opening is always safe; the **merge** then reuses `merge_pull_request`'s `pr_number` path verbatim, so the same gates and opt-in apply (`OKFFS_AUTO_MERGE_BASE`, all checks green, threads resolved, `OKFFS_BASE_MERGE_METHOD`). When merge is off or a gate is unmet, the PR is left open with an actionable reason (re-run once green, or call `merge_pull_request` with `pr_number` set to that PR's number). **Never** targets `OKFFS_PROTECTED_BRANCH` — that stays `promote_branch` + a manual merge.
- `update_guidance` (MCP prompt / slash command) reviews an issue's diff and maintains a single okffs-owned region of CLAUDE.md — the `## Project Guidance (okffs usage)` section delimited by `<!-- okffs:guidance:start -->` / `<!-- okffs:guidance:end -->` markers (created once if absent). It curates only that region (tools, env vars, prompts, conventions) and never edits the user's hand-written content elsewhere; not a changelog append; skips when nothing substantive changed. `create_pull_request` nudges the agent to run it when `OKFFS_UPDATE_GUIDANCE=true`.
- **Fragment scoping under multisite** (#330): `create_pull_request` writes the changelog fragment under the issue's app — the session's `OKFFS_APP`, else the registered app named by the issue's label (`{app}/.changes/unreleased/`), else the working directory — and reports the path and why in its response. Pure `fragmentRootFor` in `src/multisite.ts`.
- **`okffs setup` CLI wizard** (#240) — an interactive `@clack/prompts` wizard (the `bin` entrypoint above) to onboard a repo or pick up new config after an upgrade. First run offers **Quick** (auth + repo + base branch) or **Full** (every section); a re-run defaults to **sync** mode — diffs the current `.env` against the bundled manifest and only prompts for genuinely new/missing variables (explicitly-declined optional vars are written as `# KEY=` placeholders so sync tells "declined" from "never asked"). It regenerates only okffs's marked block and preserves the user's own variables/comments verbatim, runs a non-fatal GitHub **sanity test** (token/repo/branches/Projects/classic-PAT scope, plus each multisite app's directory + `.env`), and prints a config **banner** (factored for a future `okffs status`). Needs a TTY (refuses when piped). **Multisite** (#313): the manifest has a Multisite section (`OKFFS_APPS`, and `OKFFS_APP` only when the root is itself an app) and the promotion section gained `OKFFS_TAG_RELEASE` / `OKFFS_AUTO_MERGE_PROTECTED`; after the root pass the wizard offers to write `{app}/.env` (`OKFFS_APP={app}`, inheriting the root) for every registry app directory that lacks one — on every run, so a sync pass picks up newly added apps. Run inside an app directory whose repo root already has an okffs `.env` and the wizard switches to **site mode**: it asks only `OKFFS_APP` (default: the directory name, validated against the root registry) and writes that directory's `.env`. Both paths then check the repo `.gitignore` for a **depth-agnostic** `.env` rule (a bare `.env`; an anchored `/.env` covers only the root) and offer to append one (`src/cli/gitignore.ts`, pure, tested). Discoverability: the no-token/no-repo startup errors and the server instructions point users to it.
- `configure` (#242) is the tool backend for the `setup` prompt: it writes okffs configuration to the `.env` in the working directory, **reusing the same manifest + serializer as the CLI wizard** so both paths produce identical files (okffs owns only the `# okffs:env:start … end` block; the user's other vars/comments are preserved). Takes `set` (key→value) and/or `declined` (keys → commented placeholders); validates keys against the manifest (rejects unknown, no write); masks `GITHUB_TOKEN` in its output; stamps the configuring version into the block. `app: "finance"` (#313) writes `finance/.env` instead (directory must exist; `OKFFS_APP` set automatically), and unless `ensure_gitignore: false` it appends a depth-agnostic `.env` rule to the repo `.gitignore` when missing, reporting that it did. Not usually called directly.
- `setup` (MCP prompt / slash command `/okffs:setup`, #242) is the in-Claude-Code counterpart to the CLI wizard (which can't run inside the chat — it needs an interactive TTY). It embeds a rendering of the env-var manifest and drives the agent to read the current `.env`, choose breadth (quick/full/sync), interview the user section by section, then call `configure` once and remind them to restart the MCP server.
- **Upgrade nudge** (#242) — the wizard and `configure` stamp `# okffs:configured-version=X.Y.Z` into the managed `.env` block; on startup the server compares it to the running version and, when okffs is newer with unconfigured options (or the `.env` predates stamping), appends a one-time note to its MCP instructions offering `/okffs:setup`. Self-resolves once setup runs. A host can't be made to pop a "run setup?" dialog on tool reload, so this achieves the effect by okffs noticing the version bump.
- `delete_issue` closes an issue and deletes its branch. Two-step: call once for a warning, re-call with `confirmed: true` to proceed. Posts a comment before acting.
- `delete_branch` deletes a branch and closes its issue (issue number parsed from branch name prefix). Same two-step confirmation pattern. Posts a comment before acting.
- Optional `.env` defaults: `OKFFS_DEFAULT_ASSIGNEES`, `OKFFS_DEFAULT_LABELS`, `OKFFS_DEFAULT_PRIORITY`, `OKFFS_DEFAULT_EFFORT`, `OKFFS_PROMPT_METADATA`, `OKFFS_BASE_BRANCH`, `OKFFS_PROTECTED_BRANCH`, `OKFFS_IDENTIFIER`, `OKFFS_UPDATE_DOCS`, `OKFFS_AUTO_PR`.
- `OKFFS_BASE_BRANCH` — branch to create new issue branches from. Defaults to the repo's default branch.
- `OKFFS_PROTECTED_BRANCH` — a branch okffs must never autonomously **merge**, tag, or publish into (e.g. `main`). It governs *merging*, not PR *creation*: okffs will freely **open** a PR that targets it (opening is safe and reversible — the merge is the risk, and it's already gated by branch protection plus your manual merge), and `create_pull_request` adds a reminder that the merge/tag stay with you when the base is protected. `prepare_release` likewise flags merging/tagging into it as manual, user-gated steps an agent must not drive autonomously. Unset by default (#152, #181).
- `OKFFS_IDENTIFIER` — optional project-scoped prefix inserted into branch names: `{issue-number}-{identifier}-{slug}`. Unset by default.
- **Multisite** (#306/#309) — several apps in one repo (e.g. `finance/`, `health/`) sharing one issue tracker, board, branches and token, with independent version/changelog/fragments/tags/release lines. `OKFFS_APPS=finance,health` in the **git-root** `.env` is the registry; `OKFFS_APP=finance` in the app's own `.env` (which inherits the root's — #308) names the app the session runs as. With `OKFFS_APP` set: tags are `{app}-X.Y.Z` (no `v`), release branches `release/{app}-X.Y.Z`, the app name is always an issue label and the default `OKFFS_IDENTIFIER`; the changelog, fragments and version file resolve under the app root (the working directory). `create_issue`, `plan` and `create_issues_from_list` take a per-call `app` override (validated against the registry, before anything is created); `list_issues` shows `app:` per issue by its app label. Startup warnings (logged + appended to the MCP instructions, never for single-site): `OKFFS_APP` not in `OKFFS_APPS`, `OKFFS_APP` without a registry, a root session with a registry but no `OKFFS_APP`, and pending root `.changes/unreleased/` fragments that no app release would assemble (migration). A first app release (no version file yet) links its release tag instead of a compare range. Both unset ⇒ single-site behaviour is unchanged (`src/apps.ts` seam; glue in `src/multisite.ts`, pure and tested).
- `OKFFS_BASE_MERGE_METHOD` / `OKFFS_PROTECTED_MERGE_METHOD` — the PR merge method per branch tier (one of `squash` / `merge` / `rebase`). Base (e.g. `develop`) defaults to `squash`; protected (e.g. `main`) defaults to `merge` (merge commit) — the **squash-into-develop, merge-commit-into-main** convention. **Config only**: it records the method so a merge uses the right one; it does **not** grant okffs permission to merge — okffs never merges `OKFFS_PROTECTED_BRANCH` autonomously, and the autonomous base-branch merge that *consumes* `OKFFS_BASE_MERGE_METHOD` is a separate, gated capability. Invalid values warn `[okffs]` and fall back to the default (#209).
- `OKFFS_UPDATE_DOCS` — set to `true` to auto-update local project docs when a pull request is created (`create_pull_request`). Default `false`. For the changelog it writes a per-issue **fragment** at `.changes/unreleased/{issue-number}-{slug}.md` rather than editing the shared **CHANGELOG.md** directly — uniquely-named fragments never collide, so parallel issue branches don't hit add/add or same-hunk conflicts on the changelog (#105). `prepare_release` assembles the fragments into CHANGELOG.md (grouped under the right `###` heading) and deletes them in the release commit. Also updates **SECURITY.md** (security-related changes only); entries are title-based one-liners. CLAUDE.md, CONTRIBUTING.md, and README.md are intentionally **not** auto-updated (they previously got truncated changelog-style appends that duplicated CHANGELOG). `comment_issue` and `close_issue` do not trigger doc updates — `create_pull_request` is the single source of auto-changelog fragments. The `OKFFS_EXCLUDE_DOCS` key `CHANGELOG.md` still suppresses the fragment entirely.
- `OKFFS_AUTO_PR` — set to `true` to open a draft PR when a new issue branch is created (via `create_issue`). Default `false`.
- **Autopilot (minimum-interference mode)** (#238) — an opt-in *interaction style* (not a privilege escalation): when active, the agent stops asking the user to choose between options for **reversible** decisions, takes the recommended/logical option at each fork, and drives an issue all the way to a **PR into the base branch** (and a base merge where `OKFFS_AUTO_MERGE_BASE=true`), then posts an **"Autopilot decisions"** report. It can't literally suppress the host LLM's questions, so it's carried by the always-on `SERVER_INSTRUCTIONS` (the load-bearing piece) plus the `OKFFS_AUTOPILOT` env default and an active banner. Activated per-request by a phrase (`"fully handle this"` / `"minimum interference"`) **or** by `OKFFS_AUTOPILOT=true`. `create_issue`'s closing prompt offers it. Distinguishes **judgment calls** (decide + log) from **missing-information calls** (a single quick ask, or pick the most reversible option and flag it). **Hard stops always interrupt, even in autopilot:** destructive `confirmed:true` tools, and anything into `OKFFS_PROTECTED_BRANCH` (merge/tag/publish), billable, or irreversible that the user has **not** opted into. **An explicit env opt-in is the consent and is never re-asked** (#311): `OKFFS_PROMOTION_AUTO_REVIEW=true` (the billable Copilot review is the user's own GitHub billing choice), `OKFFS_AUTO_MERGE_PROTECTED=true` (a `promote_branch` re-run merges the gate PR under the full gates), `OKFFS_TAG_RELEASE=true` (the re-run tags). Correctness stops (failing check, pending requested review, unresolved thread, moved tip) are never overridden by a flag — okffs refuses and reports. `create_pull_request` and `commit_and_update` accept an `autopilot_decisions` array that okffs renders as the report block into the PR body + issue comment (`src/autopilot.ts`).
- `OKFFS_AUTOPILOT` — set to `true` to default the session to autopilot / minimum-interference mode (see above). Default `false`. Per-request activation works regardless.
- `OKFFS_RESOLVE_THREADS` — set to `true` to let okffs auto-resolve PR review threads after they're addressed (via `resolve_review_thread`). Default `false` — threads are left open for the user to resolve.
- `OKFFS_UPDATE_GUIDANCE` — set to `true` to have `create_pull_request` nudge the agent to keep CLAUDE.md in sync with new/changed functionality (via the `update_guidance` prompt). Default `false`. The prompt is always available regardless.
- `set_issue_fields` sets a board Priority and/or Effort **and/or the native Issue Type** on an **existing** issue. Priority/Effort reuse the shared `board.ts` path (project-native single-selects or org-level Issue Fields with a classic PAT) and require `OKFFS_PROJECT_ENABLED`; `type` uses the org's native Issue Types and works **independently of the board** (skipped cleanly when unavailable). Surfaces skips like `create_issue`. Fills the gap where `create_issue` only sets these at creation time; Status stays with `update_project_status`, and core fields (title/assignees/labels/milestone/body) with `update_issue` (#171, #201).
- `update_issue` mutates the **core fields** of an existing issue — `title`, `assignees`, `labels`, `milestone`, and/or `body` — via a single REST PATCH with the configured `GITHUB_TOKEN`. Fills the gap where `create_issue` only sets these at creation time, so renaming an issue or changing an assignee no longer drops to raw `gh issue edit` (wrong identity/scopes). Pass only the fields to change; omitted fields are untouched. **A `body` rewrite preserves okffs-owned metadata** (#295): the `**Branch:**` line and `## Relationships` section are extracted from the current body and re-appended when the new body omits them (pure helpers in `src/issue_body.ts`; the tool result reports what was preserved) — `preserve_metadata: false` is the explicit raw-replace escape hatch. `extractBranchFromBody` (now in `issue_body.ts`, re-exported from `github.ts`) is anchored to a line start, so a body quoting the branch-line pattern mid-prose can't shadow the real branch line. **`body` is the canonical issue-body param name everywhere** (#282): `create_issue` and the task objects of `plan` / `create_issues_from_list` take `body` too (the one-release `description` alias was removed in #297; a missing body errors naming the replacement). **`labels`/`assignees` REPLACE the whole set** (GitHub PATCH semantics — not merged), and `[]` clears them. Requires at least one field. Board Priority/Effort and the native Issue Type stay with `set_issue_fields`, and the Status column with `update_project_status` — those aren't free-form core fields (#203).
- **Native GitHub Issue Types** (Task/Bug/Feature — plus Epic/Story if the org defines them): `create_issue` (and `plan` / `create_issues_from_list`) accept a `type` and, with `OKFFS_INFER_TYPE` on (default), Claude infers the fitting org-defined type from the task — mirroring priority/effort inference; `create_issue`'s description injects the org's **real** enabled type names so inference is against the actual set. `set_issue_fields` sets `type` on an **existing** issue, and `list_issues` surfaces each issue's `type:`. Falls back to `OKFFS_DEFAULT_TYPE`. Issue Types are **org-level** — on a user-owned repo, or when the token can't read `/orgs/{org}/issue-types`, okffs skips them cleanly (non-fatal, surfaced like the board writes). okffs uses whatever types the org has defined; it can't create them. Type (what kind) is **not** the epic→story→task nesting — nesting stays with `link_issues` `parent` (#201).
- `update_project_status` moves an issue between GitHub Projects v2 board columns (`Backlog`, `Ready`, `In Progress`, `Review`) via GraphQL. Takes `issue_number` like every other issue-taking tool (#278; the one-release `issue` alias was removed in #297). `Done` is intentionally excluded — it is owned by native GitHub board automation on merge/close. Guarded by `OKFFS_PROJECT_ENABLED`; resolves the board's field/option node IDs at runtime (no hardcoding). Driven conversationally: after `create_issue` places an issue on the board, the agent offers to move it to `In Progress` and start.
- `OKFFS_PROJECT_ENABLED` — set to `true` to enable the Projects v2 integration (`list_issues` shows each issue's board column; `update_project_status` works). Default `false`; zero overhead when unset.
- `OKFFS_PROJECT_ID` — the Project's GraphQL node ID (e.g. `PVT_kwHO...`). Required when the feature is enabled.
- `OKFFS_PROJECT_AUTO_ADD` — set to `true` (fallback only) to have `create_issue` add new issues to the board via GraphQL, optionally setting a `priority`. Default `false` — leave off if your board uses GitHub's native auto-add workflow. Non-fatal: failures warn `[okffs]` and are also surfaced in the `create_issue` response (so an auto-add failure isn't invisible — see #101) and never block issue creation. Projects v2 needs a Projects-capable token (fine-grained: org "Projects: Read and write"; classic: `project` scope); missing permission surfaces a clear `[okffs]` error. **Note:** when relying on the gh-CLI fallback token (no `GITHUB_TOKEN` set), that token usually lacks the `project` scope — grant it with `gh auth refresh -s project,read:project`.
- `OKFFS_PROMOTION_STATUS` — optional board Status column (e.g. `Review`) the `promote_branch` PR card should land in. Unset by default (leave it to the board's own automation). Requires `OKFFS_PROJECT_ENABLED`. (#182)
- `OKFFS_PROMOTION_REVIEWERS` — optional comma-separated reviewers requested on the `promote_branch` gate PR (e.g. `copilot-pull-request-reviewer[bot]` for GitHub Copilot code review — the develop→main review convention). Unset by default. Only acted on when `OKFFS_PROMOTION_AUTO_REVIEW=true`. Best-effort: a failure warns `[okffs]` and is surfaced in the response, never blocking the PR. (#182)
- `OKFFS_TAG_RELEASE` — set to `true` to let a `promote_branch` re-run tag the release(s) carried by the last **merged** promotion PR on its merge commit (default `false`; a tag usually triggers an irreversible CI publish — #310).
- `OKFFS_AUTO_MERGE_PROTECTED` — set to `true` to let a `promote_branch` re-run merge the gate PR into `OKFFS_PROTECTED_BRANCH` under the full merge gates (default `false`; the explicit opt-in that makes the fully handled promotion possible — #311).
- `OKFFS_PROMOTION_AUTO_REVIEW` — explicit opt-in (default `false`) for `promote_branch` to auto-request `OKFFS_PROMOTION_REVIEWERS`. When `true`, reviewers are requested **only when the gate PR is first created** — never on updates/re-runs — so a reviewer isn't re-triggered each time; re-review after new commits is a manual step. **⚠️ Cost:** GitHub Copilot code review is billable, so enabling this with Copilot incurs a charge per newly-created promotion PR. Leave `false` to request reviews manually. (#194)
- `OKFFS_PROJECT_INITIAL_STATUS` — optional board Status column (e.g. `Backlog`) that a freshly auto-added issue should land in. `create_issue` applies it **after** the draft PR is created, so it wins over GitHub's built-in "PR linked to issue" workflow — which would otherwise flip a just-scaffolded issue straight to "In Progress" (#103). Unset by default (leave the board's own automation in charge). Must exactly match one of the board's Status option names; non-fatal `[okffs]` warning if it doesn't. Best-effort: GitHub's linked-PR automation is asynchronous, so in rare cases it may still re-flip after okffs sets the status.

### Phase 4 — Auto-close on merge ✓ Complete

- `create_pull_request` tool — reads the issue, commits on the branch, and issue comments to generate a PR title and body. Always includes `Closes #N`. Posts a summary comment back to the issue.
- If `OKFFS_UPDATE_DOCS=true`, writes a changelog **fragment** under `.changes/unreleased/` (see #105) before the PR is created and commits it onto the branch (`git add` + commit) so it's included in the PR diff. A commit failure is logged with an `[okffs]` prefix and never blocks PR creation.
- Before creating the PR, the branch is pushed to remote (`git push origin <branch>`). If the push fails, a comment is posted to the issue and the PR is not created.
- `OKFFS_AUTO_PR` no longer triggers a PR on close — the draft PR is opened at branch-creation time by `create_issue`. To accept the draft PR immediately, `create_issue` first pushes an empty init commit so the branch diverges from base.
- `commit_and_update` tool — stages all changes, generates a conventional commit message, commits, pushes to the current branch, and posts a rich progress comment to the linked issue.
- GitHub natively closes the issue on merge via `Closes #N` — no webhook infrastructure needed. Note: this only fires when merging into the repo's default branch. With a `develop`-based workflow (`OKFFS_BASE_BRANCH=develop`), merge to `develop` does not auto-close; use `close_issue`.
- Edge case: if the branch has no commits ahead of the base branch, a friendly comment is posted instead of erroring — **unless** `allow_empty: true` is passed, in which case okffs pushes an empty init commit to diverge the branch and opens a **draft** tracking PR (the same empty-init-commit mechanism `create_issue` uses under `OKFFS_AUTO_PR`, factored into a shared `pushEmptyInitCommit` helper). Opt-in per call — use it to backfill a PR onto a branch that was created empty (#205).

### Phase 5 — GitHub Projects v2 ✓ Complete

- Opt-in via `OKFFS_PROJECT_ENABLED`; org-level board addressed by `OKFFS_PROJECT_ID` (GraphQL node ID). Zero overhead when disabled.
- Projects v2 has no REST API — all board work goes through GraphQL, reusing the shared `graphqlRequest` helper (exported from `github.ts`). Projects code lives in `src/projects.ts`; field and single-select option node IDs are **discovered at runtime and memoized**, never hardcoded (they differ per board).
- `create_issue` — when `OKFFS_PROJECT_AUTO_ADD=true`, adds the new issue to the board and optionally sets a `priority` and/or `effort` (both handled by one generic helper). By default the tool description tells Claude to **infer** the `priority`/`effort` from the task itself (like it already infers labels), using the common scale, and to omit the field when it can't judge — so `OKFFS_DEFAULT_PRIORITY`/`OKFFS_DEFAULT_EFFORT` become the fallback for the ambiguous case rather than a blunt always-value. Inference is toggled per field by `OKFFS_INFER_PRIORITY` / `OKFFS_INFER_EFFORT` (default on). Injecting the board's *real* option names for arbitrary boards is tracked in #133. Two field shapes are supported for each: a **project-native single-select** field (set on the project item) and a GitHub **org-level Issue Field** (Phase 5.1, #91). When the project field reports no options — the signature of an org Issue Field — okffs resolves the option via `organization.issueFields` (any single-select field by name) and sets it on the **issue** with `setIssueFieldValue`. Non-fatal, mirroring the `autoPR` block: any failure warns `[okffs]` and never blocks issue creation. `OKFFS_PROJECT_AUTO_ADD` is a fallback for boards without GitHub's native auto-add workflow.
- `update_project_status` — moves an issue between `Backlog`, `Ready`, `In Progress`, `Review`. **`Done` is intentionally excluded** — native GitHub board automation owns it on PR merge / issue close (okffs already writes `Closes #N`). Driven conversationally by the agent at the natural workflow moments.
- `list_issues` — surfaces each issue's current board column (`project: <column>`), its `priority:`, and its `effort:`, and orders the listing by Priority (Urgent → High → Medium → Low → unset). Priority and Effort come from the project-native fields, or the org Issue Fields when `OKFFS_CLASSIC_PAT=true` (one extra batched query returning all org single-select values, gated on that flag). Non-fatal: the listing still renders if either Projects fetch fails.
- Token permission: fine-grained PAT → org "Projects: Read and write"; classic PAT → `project` scope. Missing permission surfaces a clear `[okffs]` 403 error. **Org-level Issue Fields (Priority) need a *different* permission** than Projects: a **classic PAT with `admin:org`** can read `organization.issueFields` and write via `setIssueFieldValue`; **fine-grained PATs currently return FORBIDDEN** for this preview API. This path is gated behind **`OKFFS_CLASSIC_PAT=true`** — an explicit opt-in (default off) that declares `GITHUB_TOKEN` is a broad-scoped classic `admin:org` token. When off (or the token can't reach it), the org-priority path is skipped with an actionable `[okffs]` message (set Priority in the UI, or enable the flag with an `admin:org` classic token).
- `OKFFS_CLASSIC_PAT` — default `false`. Set `true` only when `GITHUB_TOKEN` is a classic PAT with `admin:org`, to enable setting org-level Issue Field Priority (#91). **Security tradeoff:** classic `admin:org` tokens are coarse (all your repos + org admin), so this is opt-in and warned about in `.env.example`.

## Local setup

- `.env` holds the GitHub PAT (`GITHUB_TOKEN`) with fine-grained permissions. It is git-ignored — see [.env.example](.env.example).
- `.env` is loaded automatically at startup (`src/env_load.ts`, #308): the working directory's `.env` first, then the **git root's** `.env` underneath it — the closer file wins, and the real process environment wins over both. A multisite app directory (e.g. `finance/`) therefore inherits the shared token/board/branch values from the repo root and overlays only what differs. Single-site is unchanged: when the working directory is the git root there is one file, loaded once. Nothing is written to stdout (the MCP transport). No `--env-file` flag required in `.mcp.json`.
- Auth resolution: `GITHUB_TOKEN` if set, otherwise falls back to the GitHub CLI (`gh auth token`). If neither is available, startup fails with a message linking to the one-click PAT page.
- Repo resolution: `GITHUB_OWNER`/`GITHUB_REPO` if set, otherwise auto-detected by parsing the `origin` git remote of `process.cwd()`. So with `gh` signed in and okffs run inside the target repo, no `.env` is required.
- Resolution lives in `src/github.ts` (`resolveToken`, `resolveOwnerRepo`); `owner`/`repo` are exported from there and reused (e.g. `docs.ts`) so detected values flow everywhere. At server startup, `canonicalizeRepo()` makes one `GET /repos/{owner}/{repo}` and adopts GitHub's `full_name` (#273) — after a repo transfer/rename the stale owner still works in URL paths (fetch follows the 301) but silently breaks query-embedded uses like the `head=owner:branch` PR filter; canonicalizing once fixes them all. Best-effort (a failure warns and keeps the resolved values), with a `[okffs]` warning suggesting you update `GITHUB_OWNER`/`GITHUB_REPO` or the origin remote.
- Optional: `OKFFS_DEFAULT_ASSIGNEES` (comma-separated), `OKFFS_DEFAULT_LABELS` (comma-separated), `OKFFS_PROMPT_METADATA` (set to `false` to silence the tip), `OKFFS_BASE_BRANCH` (branch to create from; defaults to repo default), `OKFFS_PROTECTED_BRANCH` (a branch okffs won't autonomously merge/tag/publish into, e.g. `main`; it may still open a PR targeting it — the gate is on merging, not PR creation; unset by default — #152, #181), `OKFFS_IDENTIFIER` (optional project-scoped branch prefix: `{number}-{identifier}-{slug}`), `OKFFS_UPDATE_DOCS` (set to `true` to enable auto doc updates), `OKFFS_AUTO_PR` (set to `true` to open a draft PR at branch-creation time via `create_issue`), `OKFFS_AUTOPILOT` (set to `true` to default the session to autopilot / minimum-interference mode — take the recommended option at each reversible fork, drive to a base-branch PR, and report the decisions; hard stops still interrupt; per-request activation via a phrase works regardless — #238), `OKFFS_BASE_MERGE_METHOD` / `OKFFS_PROTECTED_MERGE_METHOD` (PR merge method per branch tier — `squash`/`merge`/`rebase`; default `squash` for base, `merge` for protected; config only, doesn't grant merge permission — #209), `OKFFS_AUTO_MERGE_BASE` (set to `true` to let `merge_pull_request` autonomously merge a green, threads-resolved issue PR into the base branch; default `false`; never merges `OKFFS_PROTECTED_BRANCH` and refuses when it's unset — #211), `OKFFS_RESOLVE_THREADS` (set to `true` to auto-resolve PR review threads after addressing; default leaves them for the user), `OKFFS_UPDATE_GUIDANCE` (set to `true` to nudge keeping CLAUDE.md in sync with functionality changes at PR time), `OKFFS_EXCLUDE_DOCS` (comma-separated filenames to exclude from auto-updates — valid options: `CHANGELOG.md`, `SECURITY.md`), `OKFFS_PROJECT_ENABLED` (set to `true` to enable the GitHub Projects v2 integration), `OKFFS_PROJECT_ID` (the board's GraphQL node ID; required when enabled), `OKFFS_PROJECT_AUTO_ADD` (set to `true` as a fallback to have `create_issue` add issues to the board when your board has no native auto-add), `OKFFS_PROJECT_INITIAL_STATUS` (board Status column a freshly auto-added issue should land in, e.g. `Backlog`; set after the draft PR so it wins over GitHub's linked-PR "In Progress" promotion — #103), `OKFFS_CLASSIC_PAT` (set to `true` only when `GITHUB_TOKEN` is a classic `admin:org` PAT, to enable org-level Issue Field Priority — #91; ## Testing

- `npm test` runs the [`node:test`](https://nodejs.org/api/test.html) suite via the existing `tsx` loader (`node --import tsx --test "src/**/*.test.ts"`) — zero extra dependencies. Tests live beside the code they cover as `*.test.ts` and are excluded from the `tsc` build (`tsconfig.json`), so they never emit into `dist/` or ship to npm.
- Coverage spans the pure-logic layer (#259, on the #253 baseline): `github.ts` can't be imported in tests (it resolves token/repo at import time), so pure helpers live in dedicated modules — `src/apps.ts` (the app descriptor seam, #307: root/tag prefix/changelog/fragments dir/release branch per app; the single-site descriptor reproduces the flat layout byte for byte), `src/version_source.ts` (package.json → VERSION fallback, temp-dir tested), `src/branch.ts` (slugify, buildBranchName, isUntouchedBranch), `src/version.ts` (bumpVersion, isNewer, replaceExactly), `src/remote.ts` (parseOwnerRepo, shared by github.ts + cli/probe.ts), `src/priority.ts` (priorityRank), `src/issue_body.ts` (body resolution, **Branch:**/Relationships metadata, parseRelationships), `src/staging.ts` (secrets deny-list, auto commit message, splitCommitMessage), `src/projects_transform.ts` (the #257 repo-scoped board transforms, fixture-proven against foreign-board leakage), plus `src/github_errors.ts`, `src/config.ts`, `src/autopilot.ts`, and the CLI's `src/cli/env.ts` round-trip — with `github.ts`/`projects.ts` re-exporting so importers are unchanged. Follow the same pattern for new logic: put pure transforms in an importable module and test them there; the GitHub API-calling layer stays untested (mocking it is a separate decision).
- CI does **not** yet gate on `npm test` — running it is a manual/local step for now.

## Codebase search

This project uses [semble](https://github.com/MinishLab/semble) for semantic code search. The MCP server is registered at the user level (`~/.claude.json`) and a dedicated sub-agent is configured at `.claude/agents/semble-search.md`.

**Claude Code should use the `semble-search` sub-agent for any exploratory or semantic codebase questions** — finding implementations, understanding how something works, locating related code — instead of grep/glob/read directly.

To search manually:

```bash
uvx --from "semble[mcp]" semble search "your query" .
```
